## 1. Цель и контекст

**Референс.** Dub Together — вечериночная игра, где до шести игроков переозвучивают видеоклипы, придавая им новый смысл: каждый записывает сцену, затем все вместе смотрят результаты и голосуют. В оригинале есть голосовые эффекты, встроенный редактор клипов и голосование через чат Twitch.

**Цель проекта.** Сделать браузерную многопользовательскую игру того же жанра, в которую можно играть по ссылке без установки и без регистрации, с собственной библиотекой клипов на сервере и удобным инструментом для их подготовки.

**Ключевые принципы:**
- *Нулевой порог входа:* открыл ссылку → ввёл имя → выбрал аватар → играешь.
- *Быстрый старт клипа:* воспроизведение начинается < 1 с после начала раунда на среднем канале.
- *Точная синхронизация:* голос игрока совпадает с губами персонажа (погрешность ≤ 40 мс).
- *Контент как данные:* новый клип добавляется без релиза клиента.

## 2. Границы проекта (scope)

### 2.1. Входит в MVP
| Область | Что делаем |
|---|---|
| Комнаты | Создание комнаты, вход по 4–6-символьному коду или ссылке, до 6 игроков + зрители |
| Профиль | Имя + аватар (набор пресетов + конструктор), хранится локально |
| Игра | Выбор клипа, запись дубляжа, общий просмотр, голосование, подсчёт очков |
| Эффекты | 4–6 голосовых эффектов (питч вверх/вниз, робот, эхо, рация) |
| Клипы | Библиотека на сервере, категории, фильтр по числу ролей и возрастному рейтингу |
| Clip Studio | Веб-инструмент для админа/автора: загрузка исходника → разметка реплик → экспорт пакета |
| Оптимизация | Транскодинг, несколько качеств, CDN, предзагрузка следующего клипа |

### 2.2. Не входит в MVP (non-goals)
- Аккаунты, друзья, глобальные рейтинги.
- Интеграция с Twitch-чатом (этап 4).
- Пользовательская загрузка клипов из игры (только через Clip Studio с модерацией).
- Мобильные нативные приложения (но мобильный браузер поддерживаем).
- Сохранение/шаринг итоговых видео в соцсети (этап 4).

## 3. Игровой цикл и правила

```
Лобби → Выбор клипа → Репетиция (опц.) → Запись → Загрузка дорожек →
Просмотр всех дубляжей → Голосование → Итоги раунда → (след. раунд | финал)
```

### 3.1. Фазы раунда
| Фаза | Длительность (по умолч.) | Детали |
|---|---|---|
| Выбор клипа | 20 с | Хост выбирает или голосование из 3 случайных клипов |
| Распределение ролей | авто | Режим «каждый озвучивает весь клип» или «по ролям» (клип с N ролями) |
| Репетиция | 1 прогон | Клип без записи, с подсказками тайминга реплик |
| Запись | длина клипа + 3 с отсчёта | Попыток: до 2, игрок выбирает лучшую |
| Загрузка | ≤ 10 с | Показ прогресса всех игроков в лобби |
| Просмотр | Σ длин клипов | Анонимно или с именами (настройка комнаты) |
| Голосование | 20 с | Нельзя голосовать за себя; зрители голосуют с меньшим весом |
| Итоги | 8 с | Очки, реакции, «лучшая фраза» |

### 3.2. Режимы
1. **Классика** — каждый игрок озвучивает клип целиком, затем голосование.
2. **Командный дубляж** — клип с 2–4 ролями, игроки распределены по ролям; сравниваются команды.
3. **Импровизация** — клип без субтитров-подсказок, только таймкоды.

### 3.3. Очки
- 100 очков за каждый голос, +50 бонус победителю раунда, +25 за «приз зрительских симпатий».
- Настройки хоста: число раундов (3/5/7), таймеры, анонимность, фильтр рейтинга клипов.

## 4. Пользовательские сценарии и требования

### 4.1. User stories (с критериями приёмки)

**US-1. Вход в игру.** Как гость, я хочу открыть ссылку, указать имя и аватар и сразу попасть в комнату.
- ✅ Путь от открытия ссылки до лобби ≤ 3 экранов/15 с.
- ✅ Имя 2–20 символов, фильтр запрещённых слов, уникализация в комнате («Аня» → «Аня 2»).
- ✅ При повторном заходе имя и аватар подставляются автоматически.

**US-2. Создание комнаты.** Как хост, я хочу создать комнату и поделиться кодом.
- ✅ Код комнаты из 5 символов без похожих (без 0/O, 1/I).
- ✅ Кнопка «Скопировать ссылку», QR-код для телефонов.
- ✅ Если хост ушёл — права переходят следующему по времени входа.

**US-3. Запись дубляжа.** Как игрок, я хочу записать голос поверх клипа с подсказками.
- ✅ Запрос доступа к микрофону с понятным объяснением; обработка отказа.
- ✅ Отсчёт 3-2-1, бегущая строка реплик, индикатор уровня громкости.
- ✅ Возможность перезаписать один раз; прослушивание перед отправкой.

**US-4. Просмотр и голосование.** Как игрок, я хочу посмотреть все версии синхронно с остальными и проголосовать.
- ✅ Все клиенты начинают воспроизведение одновременно (расхождение ≤ 300 мс).
- ✅ Голосование работает и на телефоне.

**US-5. Реконнект.** Как игрок, при обрыве связи я хочу вернуться в ту же игру.
- ✅ Переподключение в течение 60 с восстанавливает место, очки и роль.

**US-6. Автор клипов.** Как автор контента, я хочу подготовить клип и опубликовать его в игре без участия программиста (см. §9).

### 4.2. Функциональные требования (кратко)
- FR-1 Комнаты: создать, войти, выйти, кикнуть (хост), заблокировать вход во время раунда.
- FR-2 Зрители: вход без участия, голосование.
- FR-3 Чат-реакции (эмодзи) во время просмотра.
- FR-4 Библиотека клипов: категории, теги, длительность, число ролей, рейтинг 0+/12+/16+.
- FR-5 Голосовые эффекты в реальном времени при записи и при просмотре.
- FR-6 Локализация интерфейса (RU/EN на старте), клипы с субтитрами на нескольких языках.

## 5. Идентичность игрока без авторизации

### 5.1. Гостевой профиль
- При первом визите клиент генерирует `playerId` (UUID v4) и `playerSecret` (32 байта случайных данных).
- Сервер выдаёт подписанный **гостевой токен** (JWT/PASETO, срок жизни 30 дней) с `playerId`; `playerSecret` нужен для перевыпуска.
- В `localStorage` хранится `{ playerId, displayName, avatar, token }`. Никаких email/паролей.
- Токен используется для реконнекта и защиты от подмены чужого игрока в комнате.

### 5.2. Аватары
**MVP — конструктор без загрузки файлов** (решает модерацию и вес):
- Слои SVG: форма головы, цвет кожи, глаза, рот, причёска, аксессуар, фон. ~8 параметров × 6–12 вариантов.
- Аватар хранится как компактный объект: `{"v":1,"b":3,"e":5,"m":2,"h":7,"a":0,"c":"#FFB347"}` (< 100 байт), рендерится на клиенте.
- Кнопка «Случайный», 24 готовых пресета.
- В игре аватар «говорит»: анимация рта по уровню громкости во время просмотра дубляжа игрока.

**Опционально (этап 3) — своя картинка:**
- Кроп на клиенте до 256×256, конвертация в WebP (≤ 30 КБ), загрузка на сервер.
- Автоматическая проверка NSFW-классификатором + кнопка «пожаловаться»; хранение 30 дней с момента последнего использования.

### 6.4. Протокол реального времени (фрагмент)
```ts
// клиент → сервер
type C2S =
  | { t: "join"; roomCode: string; token: string; name: string; avatar: AvatarSpec }
  | { t: "ready" }
  | { t: "pickClip"; clipId: string }
  | { t: "dubUploaded"; dubId: string; offsetMs: number }
  | { t: "vote"; targetPlayerId: string }
  | { t: "reaction"; emoji: string };

// сервер → клиент
type S2C =
  | { t: "state"; room: RoomSnapshot; v: number }        // полное состояние
  | { t: "patch"; ops: JsonPatch[]; v: number }          // инкремент
  | { t: "phase"; phase: Phase; endsAt: number }         // серверное время
  | { t: "playAt"; mediaId: string; startAt: number }    // синхронный старт
  | { t: "timeSync"; serverNow: number };
```
- Сервер — единственный источник правды по фазам и таймерам.
- Синхронизация часов: NTP-подобный пинг (5 замеров, берём медиану RTT/2).

## 7. Модель данных

```sql
-- Клипы
clips(
  id uuid pk, slug text unique, title text, description text,
  duration_ms int, roles_count smallint, age_rating text, language text,
  status text check (status in ('draft','processing','review','published','archived')),
  version int, manifest_url text, poster_url text,
  source_credit text, license text, created_by text,
  created_at timestamptz, published_at timestamptz
)
clip_tags(clip_id uuid, tag text)
clip_stats(clip_id uuid, plays int, avg_score real, skips int)   -- для рекомендаций

-- Дубляжи (временные)
dubs(
  id uuid pk, room_id text, round int, player_id uuid, clip_id uuid,
  role_id text null, storage_key text, duration_ms int, offset_ms int,
  effect text, created_at timestamptz, expires_at timestamptz  -- TTL 24 ч
)

-- Жалобы
reports(id uuid pk, target_type text, target_id text, reason text, reporter_id uuid, created_at timestamptz)
```
Комнаты живут только в Redis (`room:{code}` с TTL 2 ч после последней активности).

## 8. Формат клипа (Clip Package)

Клип — это не один файл, а **пакет**: видео без диалогов, фоновая дорожка (музыка+эффекты), опциональная оригинальная дорожка голоса (для режима «до/после»), и манифест с разметкой реплик.

### 8.1. Структура пакета
```
my-clip/
├── manifest.json          — описание и тайминги (обязательно)
├── source/                — исходники (не публикуются в игру)
│   ├── original.mp4
│   └── dialogue.wav       — выделенный голос
├── video/                 — генерируется воркером
│   ├── 720p.mp4 | 480p.mp4 | 360p.mp4   (H.264, fast start)
│   ├── 720p.av1.mp4                     (опционально)
│   └── hls/ …                           (для клипов > 60 с)
├── audio/
│   ├── bed.opus           — музыка+эффекты без голоса (Opus 96 кбит/с)
│   ├── bed.m4a            — fallback AAC для старых Safari
│   └── original_voice.opus
├── poster.webp            — первый кадр/обложка
├── preview.webm           — 3-секундное беззвучное превью для списка
└── subtitles/
    ├── ru.vtt
    └── en.vtt
```

## 9. Инструмент создания клипов (Clip Studio)

Веб-приложение (`/apps/studio`), доступное авторам по секретной ссылке/ключу (отдельно от игроков; в MVP — один общий ключ, позже — роли).

### 9.1. Конвейер (pipeline)
```
1. Импорт ─▶ 2. Обрезка ─▶ 3. Отделение голоса ─▶ 4. Разметка реплик ─▶
5. Проверка/предпросмотр ─▶ 6. Экспорт пакета ─▶ 7. Транскодинг (воркер) ─▶
8. Модерация ─▶ 9. Публикация
```

### 9.2. Функции по шагам
| Шаг | Функции | Реализация |
|---|---|---|
| 1. Импорт | Загрузка MP4/MOV/MKV до 2 ГБ (resumable, tus/S3 multipart); поля «источник» и «лицензия» обязательны | tus-клиент, проверка ffprobe |
| 2. Обрезка | Таймлайн с превью-кадрами, In/Out, рекомендация 10–60 с; кадрирование 16:9 | Превью-спрайты генерирует воркер |
| 3. Отделение голоса | Автоматически: Demucs (htdemucs) → `vocals` + `no_vocals`; ручная коррекция: заглушить участки, вернуть звук (например, смех/крики как часть фона) | GPU-воркер (опционально), CPU-fallback; прогресс в UI |
| 4. Разметка реплик | Волна голосовой дорожки + видео; авто-детекция фраз (VAD, silero-vad) → черновые отрезки; авто-транскрипция (Whisper) → текст; ручная правка границ, текста, назначение ролей, подсказки интонации | Клавиши: `I`/`O` — границы, `Space` — play, `←/→` — ±1 кадр |
| 5. Предпросмотр | Режимы: «как у игрока» (без голоса + субтитры), «оригинал», «тестовая запись» (автор сам записывает дубль) | Тот же плеер, что в игре (общий пакет) |
| 6. Экспорт | Валидация манифеста (схема Zod/JSON Schema), проверки качества (см. 9.3), формирование пакета | Кнопка «Отправить на обработку» |
| 7. Транскодинг | Лестница качеств, аудио-кодеки, постер, превью, хеши | Media Worker (FFmpeg) |
| 8. Модерация | Второй человек проверяет контент, рейтинг, права | Статус `review` → `published` |
| 9. Публикация | Появляется в библиотеке; можно откатить на прошлую версию | Инвалидация только манифеста/каталога в CDN |

### 9.3. Автоматические проверки перед экспортом
- Длительность 5–90 с; минимум 1 реплика; реплики не пересекаются внутри одной роли.
- Уровень остаточного голоса в `bed` ниже −35 dBFS в интервалах реплик (иначе предупреждение «голос не до конца удалён»).
- Громкость фона нормализована до −23 LUFS ±1 (EBU R128).
- Нет «чёрного экрана» > 2 с, разрешение исходника ≥ 480p.
- Заполнены: название, рейтинг, источник, лицензия.

### 9.4. CLI для пакетного импорта (для разработчиков)
```bash
# Создать пакет из готовых файлов (если голос уже отделён вручную)
npx dubroom-clip init ./space-cat --video original.mp4
npx dubroom-clip separate ./space-cat           # Demucs локально
npx dubroom-clip lines ./space-cat --from-srt dialogs.srt --role-map roles.json
npx dubroom-clip validate ./space-cat
npx dubroom-clip publish ./space-cat --api https://api.example.com --key $STUDIO_KEY
```
CLI и Studio используют один пакет `@dubroom/clip-format`, поэтому результат идентичен.

## 10. Инструкция: как создать и экспортировать клип вручную

Для авторов, которые хотят подготовить клип в привычных инструментах (DaVinci Resolve, Premiere, Audacity) без Studio.

### Шаг 1. Подберите исходник
- Длина 10–60 с, 1–4 персонажа, чётко видны лица/губы, мало наложенной речи.
- Проверьте права: собственное видео, CC-лицензия (CC0/CC BY), public domain или письменное разрешение. Запишите источник и лицензию.

### Шаг 2. Обрежьте и экспортируйте мастер
- Экспорт: MP4, H.264, 1080p или 720p, 25/30 fps (постоянный), звук 48 кГц стерео, AAC 320 кбит/с или WAV отдельно.

### Шаг 3. Отделите голос от фона
- Вариант A (лучше): если есть исходные дорожки (M&E), экспортируйте музыку+эффекты отдельно в WAV.
- Вариант B: отделите нейросетью:
  ```bash
  pip install demucs
  demucs --two-stems=vocals -n htdemucs master.wav
  # результат: separated/htdemucs/master/no_vocals.wav и vocals.wav
  ```
- Прослушайте `no_vocals.wav` в местах реплик. Остаточные «призраки» голоса приглушите в Audacity (Effect → Amplify −12 дБ на участке) или замените на фон из соседних участков.

### Шаг 4. Разметьте реплики
- Сделайте SRT-файл, где каждая реплика начинается с метки роли:
  ```
  1
  00:00:01,200 --> 00:00:03,900
  [r1] Мы оба знаем, чья это миска.
  ```
- Удобно в Subtitle Edit или Aegisub: откройте видео + `vocals.wav`, ставьте границы по волне. Границы делайте с запасом ~100 мс.

### Шаг 5. Проверьте и нормализуйте звук
```bash
ffmpeg -i no_vocals.wav -af loudnorm=I=-23:TP=-2:LRA=11 bed.wav
```

### Шаг 6. Соберите пакет
```
my-clip/
  manifest.json      ← заполните по шаблону из §8.2 (без блока media — его допишет воркер)
  source/original.mp4
  source/bed.wav
  source/dialogue.wav
  subtitles/ru.srt
```
Или одной командой: `npx dubroom-clip init … && npx dubroom-clip lines … --from-srt subtitles/ru.srt`.

### Шаг 7. Проверьте и загрузите
```bash
npx dubroom-clip validate ./my-clip   # исправьте ошибки
npx dubroom-clip publish ./my-clip --key $STUDIO_KEY
```
Либо загрузите ZIP пакета в Clip Studio → «Импорт пакета». Клип получит статус `processing`, затем `review`. После модерации — `published`.

### Чек-лист автора
- [ ] Права и источник указаны
- [ ] Голос в фоне не слышен в местах реплик
- [ ] Реплики размечены, роли назначены
- [ ] Тестовая запись в режиме предпросмотра совпала с губами
- [ ] Возрастной рейтинг выставлен

## 11. Хранение клипов на сервере и оптимизация загрузки

### 11.1. Транскодинг (Media Worker)
**Лестница качеств** (клипы короткие, поэтому достаточно трёх ступеней):

| Профиль | Разрешение | Видео-битрейт | Ожидаемый размер 30 с |
|---|---|---|---|
| high | 1280×720 | ~1 Мбит/с (CRF 23, H.264 High) | ~3.9 МБ |
| medium | 854×480 | ~500 кбит/с | ~1.9 МБ |
| low | 640×360 | ~280 кбит/с | ~1.1 МБ |
| (опц.) AV1 720p | 1280×720 | ~550 кбит/с | ~2.1 МБ |

```bash
# пример для 480p, видео без звука (звук идёт отдельной дорожкой bed)
ffmpeg -i trimmed.mp4 -an -vf "scale=-2:480,fps=30" \
  -c:v libx264 -profile:v main -preset slow -crf 24 \
  -maxrate 600k -bufsize 1200k -g 60 -keyint_min 60 -sc_threshold 0 \
  -movflags +faststart 480p.mp4

# фон в Opus
ffmpeg -i bed.wav -c:a libopus -b:a 96k -vbr on bed.opus
```

**Почему так:**
- Видео **без аудио**: фон хранится отдельно → один и тот же фон для всех качеств, проще микшировать голоса игроков в Web Audio.
- `+faststart` (moov-атом в начале) → воспроизведение до полной загрузки.
- Фиксированный GOP 2 с → точная перемотка и возможность HLS/CMAF без перекодирования.
- Для клипов > 60 с — HLS/CMAF сегменты по 2 с (hls.js), для коротких — прогрессивный MP4 (меньше запросов, проще кеш).

### 11.2. Хранилище и CDN
- Ключи в S3: `clips/{clipId}/v{version}/{file}.{contentHash}.{ext}`.
- Заголовки для медиа: `Cache-Control: public, max-age=31536000, immutable`; для `catalog.json` и манифестов «последней версии» — `max-age=60, stale-while-revalidate=600`.
- Поддержка HTTP Range, HTTP/2–3, Brotli для JSON.
- Каталог клипов отдаётся как один сжатый `catalog.json` (метаданные + ссылки на постеры/превью), ~20–50 КБ для 500 клипов; пагинация при росте.

### 11.3. Стратегия загрузки на клиенте
1. **Лобби:** грузим `catalog.json` и постеры (WebP, ~15 КБ, `loading="lazy"`).
2. **Выбор клипа:** при наведении/показе карточек — только 3-секундное превью (≤ 150 КБ).
3. **Кандидаты раунда:** как только сервер определил 3 кандидата, клиент с помощью `fetch` + `priority: "low"` предзагружает **первые ~500 КБ** медиум-качества каждого (Range-запрос) и `bed` целиком (он маленький).
4. **Выбранный клип:** полная загрузка видео и фона до начала репетиции; сервер не переводит фазу, пока все клиенты не прислали `ready` (или таймаут 10 с → игрок с медленной сетью получает low).
5. **Следующий раунд:** во время голосования фоново предзагружаем кандидатов следующего раунда.

### 11.4. Выбор качества
- До старта: `navigator.connection.effectiveType` (где доступно) + замер скорости по загрузке постеров/превью.
- Правило: выбрать максимальное качество, которое скачивается за ≤ 50 % времени фазы выбора; `saveData` → low.
- `MediaCapabilities.decodingInfo()` — проверка поддержки AV1 и «smooth/powerEfficient»; иначе H.264.

### 11.5. Кеширование на клиенте
- Service Worker (Workbox): стратегия `CacheFirst` для файлов с хешем в имени, лимит кеша 300 МБ, LRU-вытеснение.
- Сыгранные клипы остаются в кеше → повторные игры с теми же клипами мгновенны.
- `StorageManager.persist()` не запрашиваем (не нужно пугать пользователя).

### 11.6. Оптимизация записей игроков (дубляжей)
- Кодек записи: Opus в WebM, 48 кГц моно, 32–48 кбит/с → 30 с ≈ 150 КБ.
- Safari: `audio/mp4` (AAC) — сервер нормализует в Opus при необходимости.
- Загрузка напрямую в S3 по **presigned URL** (минуя API-сервер), ключ `dubs/{roomId}/{round}/{playerId}.webm`.
- Во время просмотра клиенты скачивают все дубляжи параллельно (5 × 150 КБ ≈ 0.75 МБ) — укладывается в фазу загрузки.
- Удаление по lifecycle-правилу S3 через 24 ч.

### 11.7. Бюджеты производительности
| Показатель | Бюджет |
|---|---|
| JS первоначальной загрузки (gzip) | ≤ 180 КБ |
| LCP лобби на 4G | ≤ 2.0 с |
| Трафик на один раунд (medium) | ≤ 3 МБ |
| Время от «клип выбран» до готовности у 95 % игроков | ≤ 5 с |
| Стоимость CDN-трафика | Мониторинг, алерт при > X ₽/день |

## 12. Запись голоса и синхронизация

Самая технически рискованная часть — ей нужен отдельный прототип на этапе 0.

### 12.1. Процесс записи
1. `getUserMedia({ audio: { echoCancellation: false, noiseSuppression: true, autoGainControl: true } })` — эхоподавление выключено, т.к. фон играет в наушники; если нет наушников — включаем и приглушаем фон.
2. Воспроизведение видео + `bed` через единый `AudioContext`; время старта фиксируется в часах AudioContext.
3. Запись через `AudioWorklet` (сырые PCM-сэмплы с меткой `currentTime`) → кодирование в Opus (WebCodecs `AudioEncoder`, fallback — MediaRecorder).
4. Сохраняем `offsetMs` = разница между началом записи и началом клипа с учётом задержек.

### 12.2. Компенсация задержек
- `audioContext.outputLatency` + `baseLatency` — задержка вывода.
- Задержка ввода неизвестна API → **калибровка** (один раз, сохраняется в `localStorage`): игрок хлопает в такт 4 щелчкам, считаем среднее отклонение. Альтернатива — «петлевой» тест при отсутствии наушников.
- Ручная подстройка ±200 мс ползунком после записи (с прослушиванием).
- Итоговая формула: `alignedStart = recStart − inputLatency − outputLatency + manualOffset`.

### 12.3. Голосовые эффекты
- Цепочки Web Audio: pitch shift (AudioWorklet на основе granular/PSOLA), ring modulator (робот), band-pass + дисторшн (рация), ConvolverNode (эхо/зал).
- Эффект применяется **на воспроизведении**, а в файле хранится «сухой» голос + название эффекта → можно менять эффект после записи, меньше артефактов кодирования.

### 12.4. Совместимость
| Браузер | Запись | Примечания |
|---|---|---|
| Chrome/Edge (десктоп, Android) | Opus/WebM | Основная цель |
| Firefox | Opus/WebM/Ogg | Проверить `outputLatency` |
| Safari (macOS/iOS 17+) | AAC/MP4 | AudioContext только после жеста пользователя; тестировать отдельно |

## 13. Воспроизведение результатов и голосование

- Сервер присылает `playAt { mediaId, startAt }` в серверном времени, клиенты стартуют с учётом смещения часов.
- Каждый дубляж = видео клипа (из кеша) + `bed` + голос игрока с эффектом, смикшированные в Web Audio; громкость голоса нормализуется (по RMS записи).
- Во время показа — аватар и имя говорящего (если не анонимно), анимация рта по огибающей.
- Если чей-то файл не загрузился — пропуск с сообщением «запись потерялась в пути», игрок не теряет очки за раунд полностью (получает среднее).
- Голосование: 1 голос на игрока, нельзя за себя; результаты сервер раскрывает после окончания таймера.
- Итоговый экран: таблица очков, «лучший дубль игры» — кнопка «пересмотреть».

## 14. Безопасность, модерация, приватность, права

> Здесь — безопасность на уровне приложения и контента. Защита самого сервера (ОС, SSH, фаервол, Docker, Cloudflare) — в §22.

- **Анти-абьюз:** rate limit на создание комнат (по IP), на WebSocket-сообщения; валидация всех сообщений схемами; максимальный размер загрузки дубляжа 2 МБ, проверка MIME и длительности на сервере.
- **Presigned URL** с ограничением типа, размера и времени жизни (5 мин).
- **Имена:** фильтр мата/оскорблений (словари RU/EN), хост может переименовать/кикнуть.
- **Голос игроков:** хранится 24 ч, только внутри комнаты; в интерфейсе — уведомление «запись доступна только участникам комнаты и удаляется через сутки».
- **GDPR/152-ФЗ:** без персональных данных в явном виде; политика конфиденциальности; голос — потенциально биометрические данные → минимальный срок хранения, без анализа.
- **Права на клипы:** в каталог попадают только клипы с указанной лицензией; процедура DMCA/жалобы — снятие за 24 ч. Стартовая библиотека: собственные съёмки, открытые фильмы (Blender Open Movies, CC BY), public domain-хроника.
- **Возрастной рейтинг:** фильтр в настройках комнаты, по умолчанию 12+.

## 16. Тестирование

## 19. Метрики успеха

- **Активация:** ≥ 70 % открывших ссылку доходят до лобби.
- **Завершение игры:** ≥ 60 % начатых игр доходят до финала.
- **Повторные игры:** ≥ 35 % комнат запускают вторую игру подряд.
- **Качество медиа:** p95 времени готовности клипа ≤ 5 с; доля low-качества ≤ 15 %.
- **Синхронизация:** ≤ 5 % игроков вручную сдвигают запись более чем на 100 мс.
- **Контент:** время публикации одного клипа ≤ 30 мин; ≥ 5 новых клипов в неделю после запуска.
- **Удовольствие:** средняя оценка плейтестов ≥ 4/5, «хочу сыграть ещё» ≥ 75 %.

## 20. Интерфейс игры

Раздел фиксирует интерфейс как часть требований: экраны, их состав, поведение и визуальный язык. Любое изменение этого раздела согласуется так же, как изменение правил игры.

### 20.1. Принципы интерфейса
1. **Одно главное действие на экран.** Крупная основная кнопка, всё второстепенное — вторичными кнопками или в меню.
2. **Статус всегда виден.** Верхняя панель показывает фазу, таймер и кто ещё не готов.
3. **Видео — главный герой.** На экранах записи и просмотра видео занимает ≥ 60 % высоты окна.
4. **Телефон — полноценный клиент.** Все экраны работают в портретной ориентации от 360 px; запись на телефоне — в ландшафтной (подсказка повернуть устройство).
5. **Праздничный, но читаемый стиль.** Яркие акценты на тёмном фоне (как в кинозале), тексты — контраст ≥ 4.5:1.
6. **Никаких тупиков.** У каждой ошибки есть объяснение и кнопка действия («Разрешить микрофон», «Переподключиться», «Выбрать качество ниже»).

### 20.6. Состояния и обратная связь
- **Загрузка:** скелетоны карточек; на фазе «Загрузка» — прогресс каждого игрока на его аватаре.
- **Ожидание других:** «Ждём Лёшу…» + мини-игра/перелистывание забавных фактов, если ожидание > 5 с.
- **Ошибки:** микрофон запрещён → экран с пошаговой подсказкой для конкретного браузера; потеря связи → плашка «Переподключаемся…» с таймером 60 с; комната не найдена → экран 404 с полем ввода кода.
- **Звуковые сигналы интерфейса** (отключаемые): тик последних 5 с таймера, «щелчок» начала записи, фанфары победителя.

### 20.7. Доступность и локализация интерфейса
- Полная навигация с клавиатуры, видимый фокус, `aria-live` для смены фаз и таймера.
- Размер шрифта субтитров регулируется (3 шага), фон под субтитрами.
- Все строки — в файлах локализации (ICU MessageFormat), плюрализация для русского.

### 20.8. Критерии приёмки интерфейса
- Все экраны из §20.3 реализованы и сверены с утверждёнными макетами (визуальные snapshot-тесты Playwright).
- Юзабилити-тест: 5 человек, впервые видящих игру, проходят путь «ссылка → записал первый дубль» без подсказок за ≤ 3 мин.
- Lighthouse Accessibility ≥ 95 на главной, профиле и лобби.

## 21. Развёртывание: скрипты установки, запуска и Cloudflare Tunnel

### 21.1. Цель
Сервис должен разворачиваться на любой Linux-машине (VPS, выделенный сервер, домашний ПК/мини-ПК) **без белого IP и без открытых входящих портов**. Публикация в интернет — через Cloudflare Tunnel: демон `cloudflared` устанавливает исходящее соединение с Cloudflare, а Cloudflare проксирует HTTPS и WebSocket-трафик на внутренние сервисы. TLS-сертификаты, защита от DDoS и кеш CDN — на стороне Cloudflare.

**Требования к результату:**
- Полная установка на чистый сервер — одна команда + ответы на 3–5 вопросов, ≤ 15 минут.
- Все скрипты идемпотентны: повторный запуск не ломает работающую установку.
- Секреты не попадают в git и логи; генерируются автоматически.
- Каждый скрипт поддерживает `--help`, неинтерактивный режим (`--yes`, переменные окружения) и возвращает ненулевой код при ошибке.

### 21.2. Топология

```
Интернет ──HTTPS/WSS──▶ Cloudflare (TLS, DDoS, кеш, Access)
                              │  исходящий туннель (QUIC/HTTP2), входящих портов нет
                              ▼
┌──────────────────────── Сервер (Docker Compose) ───────────────────────┐
│  cloudflared ×2 (реплики) ──▶ caddy:80 (внутренний reverse proxy)       │
│                                   ├── /            → web (статика SPA)  │
│                                   ├── /api/*       → api:3000           │
│                                   ├── /ws          → game-server:3001   │
│                                   ├── /media/*     → minio:9000 (чтение)│
│                                   └── /help/*      → docs (статика)     │
│  studio.<домен> ──▶ caddy ──▶ studio (закрыт Cloudflare Access)          │
│  postgres · redis · minio · media-worker · (опц.) prometheus/grafana    │
└────────────────────────────────────────────────────────────────────────┘
```

**Хостнеймы (пример для домена `example.com`):**
| Хостнейм | Назначение | Доступ |
|---|---|---|
| `play.example.com` | Игра, API, WebSocket, медиа, справка | Публичный |
| `studio.example.com` | Clip Studio | Только через Cloudflare Access (вход по email-коду для авторов) |
| `grafana.example.com` (опц.) | Мониторинг | Cloudflare Access, только администраторы |

Один публичный хостнейм для игры упрощает CORS и cookies; разделение по путям делает Caddy.

### 21.3. Режимы туннеля
| Режим | Как настраивается | Когда использовать |
|---|---|---|
| **A. Управляемый через токен (рекомендуется)** | Туннель и маршруты создаются в панели Cloudflare Zero Trust, на сервер передаётся только `TUNNEL_TOKEN` | Продакшн; проще переносить сервер, настройки видны в панели |
| **B. Локально управляемый** | `cloudflared tunnel login` → `tunnel create` → `tunnel route dns` → `config.yml` с `ingress` | Когда нужна конфигурация в git (IaC) |
| **C. Быстрый (Quick Tunnel)** | `cloudflared tunnel --url http://localhost:80` → случайный адрес `*.trycloudflare.com` | Только демо и тесты с друзьями; без домена, без гарантий |

### 21.4. Набор скриптов (`/scripts`)
| Скрипт | Назначение |
|---|---|
| `install.sh` | Проверка ОС и ресурсов, установка Docker + Compose plugin, `cloudflared`, утилит (`jq`, `openssl`), создание пользователя `dubroom`, каталога `/opt/dubroom`, загрузка релиза |
| `setup.sh` | Интерактивный мастер: домен, режим туннеля, токен/логин Cloudflare, email-ы авторов для Access, генерация `.env` с секретами, создание DNS-маршрутов, первичная миграция БД, создание бакетов MinIO |
| `start.sh` | `docker compose up -d`, ожидание healthcheck всех сервисов, проверка доступности публичного адреса, вывод ссылок |
| `stop.sh` | Корректная остановка (сначала закрыть новые комнаты, дождаться окончания текущих раундов ≤ 5 мин или `--force`) |
| `restart.sh` | `stop` + `start` |
| `status.sh` | Состояние контейнеров, туннеля (`cloudflared tunnel info`), БД, места на диске, версии; режим `--notify` для cron (Telegram/почта при сбое) |
| `logs.sh` | Логи сервиса: `./logs.sh api -f` |
| `update.sh` | Бэкап → загрузка новой версии → миграции → перезапуск без простоя (rolling для game-server) → смоук-тест; при ошибке — автоматический откат |
| `backup.sh` | Дамп PostgreSQL, снапшот бакета клипов MinIO (дубляжи не бэкапятся), `.env` в зашифрованном архиве; ротация (7 ежедневных, 4 еженедельных); опционально выгрузка в внешний S3 |
| `restore.sh` | Восстановление из архива на чистой установке |
| `tunnel.sh` | Управление туннелем: `create`, `route`, `rotate-token`, `quick` (режим C), `info` |
| `seed-clips.sh` | Импорт стартового набора клипов через `dubroom-clip publish` |
| `harden.sh` | Базовое усиление безопасности ОС, SSH, фаервола и Docker (§22); вызывается из `setup.sh`, можно запускать повторно |
| `security-check.sh` | Аудит: открытые порты, настройки SSH, обновления, образы (Trivy), Lynis, docker-bench; отчёт и ненулевой код при критичных находках |
| `rotate-secrets.sh` | Ротация паролей БД, ключей MinIO, ключа подписи токенов, токена туннеля (§22.8) |
| `uninstall.sh` | Удаление сервиса; данные удаляются только с флагом `--purge` и подтверждением |
| `dev.sh` | Локальная разработка: hot-reload, MinIO и БД в Docker, быстрый туннель для теста с телефона |

Дополнительно: `Makefile` с короткими алиасами (`make start`, `make update`), systemd-юнит `dubroom.service` для автозапуска после перезагрузки, cron-задачи для `backup.sh` и `status.sh --notify`.

### 21.6. Конфигурация (фрагменты)
**`docker-compose.yml` — сервис туннеля (режим A):**
```yaml
cloudflared:
  image: cloudflare/cloudflared:2026.9.0   # версия фиксируется, обновляется через update.sh
  command: tunnel --no-autoupdate --metrics 0.0.0.0:2000 run
  environment:
    - TUNNEL_TOKEN=${TUNNEL_TOKEN}
  restart: unless-stopped

  depends_on: [caddy]
  healthcheck:

    interval: 30s
```

**`infra/cloudflared/config.yml` (режим B):**
```yaml
tunnel: dubroom

  - hostname: play.example.com
    service: http://caddy:80
  - hostname: studio.example.com

  - service: http_status:404
```

### 21.7. Особенности работы через Cloudflare, которые учитываются в коде
- **WebSocket** проксируется туннелем штатно; клиент шлёт ping каждые 20 с (соединения без трафика рвутся по таймауту), при обрыве — автоматический реконнект (§4, US-5).
- **Реальный IP игрока** берётся из заголовка `CF-Connecting-IP` (для rate limit), Caddy доверяет только ему.
- **Лимит размера запроса** на бесплатном тарифе — 100 МБ: загрузка исходников в Clip Studio идёт частями (tus/multipart по 50 МБ); дубляжи игроков ≤ 2 МБ укладываются с запасом.
- **Кеширование:** правила Cache Rules — `/media/*` и статика с хешем в имени кешируются на краю Cloudflare (`immutable`), `/api/*` и `/ws` — в обход кеша. После публикации клипа `update`-хук сбрасывает кеш только для `catalog.json`.
- **Медиа-трафик:** для MVP и небольшой аудитории медиа отдаётся через туннель из MinIO. Перед публичным запуском сверить актуальные условия Cloudflare по раздаче видео; при росте — перенос бакета клипов в Cloudflare R2 (S3-совместимый, без платы за исходящий трафик), что меняет только `MEDIA_BASE_URL`.
- **Безопасность:** входящие порты сервера закрыты фаерволом, Studio и Grafana — за Cloudflare Access, HTTPS и HSTS принудительно. Полный перечень настроек — в §22.

### 21.8. Критерии приёмки
- На чистых Ubuntu 24.04 и Debian 12 (VM в CI) цепочка `install → setup --yes → start` проходит без ручных действий, смоук-тест (создать комнату двумя ботами, сыграть раунд) зелёный.
- Повторный `setup.sh` и `start.sh` не меняют работающую установку (идемпотентность).
- `update.sh` с намеренно сломанной миграцией откатывается к предыдущей версии.
- `backup.sh` → `restore.sh` на другой машине восстанавливает клипы и каталог.
- Перезагрузка сервера → сервис и туннель поднимаются сами ≤ 2 мин.
- Скрипты проверены `shellcheck` в CI.

## 22. Настройки безопасности сервера

Раздел описывает, как защищён сервер, на котором работает игра, и что именно настраивают скрипты `harden.sh` и `security-check.sh`. Прикладная безопасность игры (модерация, имена, записи игроков) описана в §14.

### 22.1. Модель угроз (кратко)
| Что защищаем | От чего | Главная мера |
|---|---|---|
| Сервер целиком | Сканирование портов, подбор паролей SSH, эксплойты в открытых сервисах | Ни одного открытого входящего порта; SSH только по ключу или через Cloudflare Access |
| Clip Studio и мониторинг | Посторонний доступ, загрузка вредного контента | Cloudflare Access + отдельные роли; изоляция медиа-обработки |
| Клипы, БД, секреты | Утечка, порча, шифровальщики | Сегментация сетей Docker, минимальные права, зашифрованные офсайт-бэкапы |
| Доступность игры | DDoS, флуд комнатами и сообщениями | WAF и rate limiting Cloudflare + лимиты в приложении |
| Цепочка поставки | Уязвимые зависимости и образы | Фиксированные версии, сканирование, автоматические PR с обновлениями |
| Аккаунт Cloudflare | Захват аккаунта или токена туннеля | 2FA, API-токены с минимальными правами, ротация |

### 22.2. Операционная система
- Поддерживаемые ОС: Ubuntu 24.04 LTS, Debian 12; минимальная установка без графики и лишних пакетов.
- **Автоматические обновления безопасности:** `unattended-upgrades` только для security-репозиториев, автоперезагрузка ночью (03:30 МСК), если требуется ядром; уведомление администратору.
- Отдельный системный пользователь `dubroom` без shell-входа для файлов сервиса; администраторы — личные учётки с `sudo`, общий `root`-вход запрещён.
- Синхронизация времени (`systemd-timesyncd`/`chrony`) — важна для токенов и синхронизации игры.
- Сетевые параметры ядра (`/etc/sysctl.d/90-dubroom.conf`):
  ```
  net.ipv4.conf.all.rp_filter = 1
  net.ipv4.conf.all.accept_redirects = 0
  net.ipv4.conf.all.send_redirects = 0
  net.ipv4.conf.all.accept_source_route = 0
  net.ipv4.tcp_syncookies = 1
  net.ipv6.conf.all.accept_redirects = 0
  kernel.kptr_restrict = 2
  kernel.dmesg_restrict = 1
  fs.protected_hardlinks = 1
  fs.protected_symlinks = 1
  ```
- Отключены неиспользуемые службы (`avahi`, `cups`, `rpcbind` и т. п.), `/tmp` смонтирован с `noexec,nosuid,nodev`.
- Для домашнего сервера / мини-ПК: шифрование диска (LUKS), пароль на BIOS/UEFI, отключена загрузка с USB.

### 22.3. Доступ по SSH
Два варианта, выбирается в `setup.sh`:

| Вариант | Порт 22 снаружи | Как подключаться |
|---|---|---|
| **A. SSH через Cloudflare Access (рекомендуется)** | Закрыт | `cloudflared access ssh` в `~/.ssh/config`; вход подтверждается через Access (email-код/SSO + 2FA); политика — только список администраторов |
| **B. Классический SSH** | Открыт только для SSH | Только ключи, fail2ban/CrowdSec; по возможности — разрешён только с IP администраторов |

Настройки `sshd` в обоих случаях (`/etc/ssh/sshd_config.d/90-dubroom.conf`):
```
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey
AllowGroups ssh-admins
MaxAuthTries 3
LoginGraceTime 20
ClientAliveInterval 300
ClientAliveCountMax 2
X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding no
```
- Ключи — только Ed25519 (или аппаратные ключи `sk-ssh-ed25519`), по одному на человека; при уходе человека ключ удаляется в тот же день.
- `harden.sh` перед применением проверяет, что у текущего администратора есть рабочий ключ, и не закрывает сессию, пока новое подключение не подтверждено (защита от блокировки себя).

### 22.4. Фаервол
- `ufw`: `default deny incoming`, `default allow outgoing`; входящие разрешены только для SSH в варианте B.
- Для строгого режима — ограничение исходящих: DNS (53), NTP (123), HTTPS (443), порт туннеля Cloudflare (7844 TCP/UDP), SMTP для уведомлений. Включается флагом `harden.sh --strict-egress`.
- **Важно про Docker:** опубликованные порты контейнеров (`ports:`) обходят правила `ufw`. Поэтому:
  - в `docker-compose.yml` нет ни одного `ports:` — наружу ходит только `cloudflared` исходящим соединением;
  - для локальной отладки порты публикуются только на `127.0.0.1`;
  - дополнительная страховка — правило в цепочке `DOCKER-USER`, запрещающее входящие соединения к контейнерам с внешнего интерфейса;
  - `security-check.sh` проверяет это через `ss -tulpn` и внешнее сканирование.
- Защита от подбора: fail2ban (или CrowdSec) для `sshd` — бан на 1 ч после 3 неудачных попыток, повторно — на 24 ч.

### 22.5. Docker и контейнеры
Общие правила для всех сервисов в `docker-compose.yml`:
```yaml
x-hardening: &hardening
  read_only: true                 # корневая ФС только для чтения
  tmpfs: [/tmp]
  security_opt: ["no-new-privileges:true"]
  cap_drop: [ALL]
  user: "10001:10001"             # не root внутри контейнера
  restart: unless-stopped
  logging: { driver: json-file, options: { max-size: "10m", max-file: "5" } }
  deploy:
    resources: { limits: { cpus: "1.0", memory: 512M } }   # свои лимиты у каждого сервиса

services:
  api:
    <<: *hardening
    image: ghcr.io/org/dubroom-api@sha256:…   # образ по digest, а не по тегу
    networks: [edge, backend]
```
- **Сети разделены:**
  | Сеть | Кто в ней | Выход в интернет |
  |---|---|---|
  | `edge` | cloudflared, caddy | Только cloudflared |
  | `backend` | caddy, web, api, game-server, studio | Нет (`internal: true`) |
  | `data` | api, game-server, media-worker, postgres, redis, minio | Нет (`internal: true`) |
  | `worker` | media-worker | Нет — медиа обрабатывается без доступа к сети |
- Docker-сокет не монтируется ни в один контейнер.
- Демон Docker: `userns-remap` или rootless-режим (выбирается при установке), `"live-restore": true`, `"icc": false`, ограничение логов.
- Базовые образы — минимальные (distroless / alpine), фиксированы по digest; сборка в CI, публикация с подписью (cosign), при деплое подпись проверяется.
- Сканирование образов Trivy в CI и еженедельно на сервере; критичные уязвимости блокируют релиз.

### 22.6. Изоляция обработки медиа
Clip Studio принимает видеофайлы от авторов — это недоверенные данные, а FFmpeg и нейросетевые модели — большая поверхность атаки.
- `media-worker` работает в сети без интернета (`worker`), читает и пишет только свои префиксы в MinIO через выделенный ключ.
- Каждая задача — отдельный процесс с таймаутом (например, 10 мин), лимитами CPU/памяти и `seccomp`-профилем по умолчанию.
- Перед обработкой: `ffprobe` проверяет контейнер и кодеки по белому списку (MP4/MOV/MKV; H.264/H.265/VP9/AV1; AAC/Opus/PCM), длительность ≤ 10 мин, разрешение ≤ 4K; всё остальное отклоняется.
- Выходные файлы всегда перекодируются (никакой исходный файл не отдаётся игрокам напрямую).

### 22.7. Базы данных и хранилища
- **PostgreSQL:** не публикуется наружу, аутентификация `scram-sha-256`; отдельные роли: `dubroom_app` (только DML на свои таблицы), `dubroom_migrate` (DDL, используется только `update.sh`), `dubroom_readonly` (для аналитики и бэкапов).
- **Redis:** пароль (`requirepass`) или ACL-пользователи, `protected-mode yes`, опасные команды (`FLUSHALL`, `CONFIG`, `KEYS`) отключены для пользователя приложения.
- **MinIO:** root-учётка используется только скриптами установки; сервисам выдаются отдельные ключи с политиками:
  | Ключ | Права |
  |---|---|
  | `api` | Чтение `clips/`, создание presigned URL на запись в `dubs/` |
  | `media-worker` | Чтение `uploads/`, запись `clips/` |
  | `backup` | Только чтение `clips/` |

  Листинг бакетов анонимно запрещён; публичное чтение — только через Caddy/`/media/*` с проверкой пути.
- Шифрование хранилища на диске (MinIO SSE или LUKS для всего раздела данных).

### 22.8. Секреты
- Все секреты генерируются `setup.sh` (`openssl rand`), хранятся в `/opt/dubroom/.env` (владелец `root`, права `600`) или как Docker secrets (файлы в `/run/secrets`), не в переменных образов.
- `.env` и ключи в `.gitignore`; в CI — сканер секретов (gitleaks) на каждом коммите.
- Логи и отчёты об ошибках (Sentry) фильтруют токены, пароли, presigned URL.
- Ротация: `rotate-secrets.sh` меняет пароли БД, ключи MinIO, ключ подписи токенов (со сроком двойной валидности 24 ч, чтобы не выкинуть игроков), токен туннеля. Плановая ротация — раз в 90 дней и немедленно при подозрении на утечку.

### 22.9. Защита на стороне Cloudflare
| Настройка | Значение |
|---|---|
| Аккаунт | 2FA обязательно для всех участников; роли с минимальными правами; API-токены ограничены зоной и нужными разрешениями |
| SSL/TLS | «Always Use HTTPS», минимальная версия TLS 1.2, HSTS (после проверки — `includeSubDomains`, `max-age` 6 мес.) |
| DNSSEC | Включён |
| WAF | Управляемые правила (Managed Rules) там, где доступны на тарифе; собственные правила: блок запросов к `/api/admin*` и Studio-API с публичного хостнейма, ограничение методов (`GET/POST/PUT/OPTIONS`) |
| Rate limiting | Создание комнат: 10/мин на IP; вход в комнату: 30/мин; загрузка дубляжей: 20/мин; превышение — challenge или блок на 10 мин |
| Боты | Bot Fight Mode; Turnstile (невидимая проверка) на создании комнаты при подозрительном трафике |
| Access | Приложения: `studio.*`, `grafana.*`, SSH; политика — список email + обязательная 2FA у провайдера; длительность сессии 12 ч; сервисный токен для CI со строгим сроком действия |
| Туннель | Токен хранится только на сервере; при компрометации — `tunnel.sh rotate-token`; в панели включены уведомления о статусе туннеля |
| Происхождение запросов | Приложение доверяет `CF-Connecting-IP` только если запрос пришёл от `cloudflared`; прямой доступ к сервисам извне невозможен (нет открытых портов) |

### 22.10. Заголовки и настройки веб-приложения
Caddy добавляет заголовки безопасности ко всем ответам:
```caddyfile
header {
  Content-Security-Policy "default-src 'self'; img-src 'self' data: blob:; media-src 'self' blob:; connect-src 'self' wss://play.example.com; script-src 'self'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self'"
  Strict-Transport-Security "max-age=15552000; includeSubDomains"
  X-Content-Type-Options "nosniff"
  Referrer-Policy "strict-origin-when-cross-origin"
  Permissions-Policy "microphone=(self), camera=(), geolocation=(), payment=()"
  Cross-Origin-Opener-Policy "same-origin"
  -Server
}
```
- CORS: разрешён только собственный хостнейм; WebSocket проверяет `Origin`.
- Лимиты: размер WS-сообщения ≤ 16 КБ, не более 20 сообщений/с на соединение, не более 3 соединений с одного `playerId`.
- Все входные данные проверяются схемами Zod; ошибки не раскрывают стек и версии.
- Админские API-эндпоинты доступны только с хостнейма Studio (проверка заголовка `Cf-Access-Jwt-Assertion` и его подписи).

### 22.11. Мониторинг, журналы и реагирование на инциденты
- **Журналы:** системные (`journald`, `auth.log`), контейнеров, Caddy (доступ), Cloudflare (Access, WAF-события). Хранение — 30 дней; IP-адреса в журналах приложения хешируются.
- **Оповещения** (Telegram/почта через `status.sh --notify` и Grafana): вход по SSH, бан fail2ban, рост 4xx/5xx, всплеск блокировок WAF, туннель недоступен, диск > 80 %, неудачный бэкап, найдены критичные уязвимости.
- **Аудит:** `auditd` для изменений в `/etc`, `/opt/dubroom/.env`, `sudo`-команд.
- **Бэкапы (правило 3-2-1):** шифрование `age`, копия во внешнем S3 (другой провайдер/регион), ежемесячный тест восстановления на временной VM.
- **Порядок действий при инциденте** (runbook в руководстве администратора):
  1. Изолировать: включить режим обслуживания (`stop.sh --maintenance`), при необходимости отключить туннель.
  2. Сохранить журналы и снимок диска.
  3. Ротировать все секреты (`rotate-secrets.sh --all`), токен туннеля, ключи SSH.
  4. Восстановить из последнего чистого бэкапа, обновить систему и образы.
  5. Разбор причин, запись в журнал инцидентов, при утечке данных — уведомление пользователей в установленные законом сроки.

### 22.12. Чек-лист безопасности сервера (проверяется `security-check.sh`)
- [ ] Внешнее сканирование (`nmap` с другой машины) не находит открытых портов (кроме SSH в варианте B)
- [ ] `PasswordAuthentication no`, `PermitRootLogin no`; вход только по ключу / через Access
- [ ] `ufw` активен, политика входящих — deny; в compose нет публичных `ports:`
- [ ] Автоматические обновления безопасности включены, нет ожидающих критичных обновлений
- [ ] Контейнеры запущены не от root, `no-new-privileges`, `cap_drop: ALL`, образы по digest
- [ ] Trivy: нет уязвимостей уровня Critical; docker-bench-security без ошибок уровня WARN в разделах 2, 4, 5
- [ ] Lynis hardening index ≥ 75
- [ ] `.env` с правами 600, секретов нет в git (gitleaks), возраст секретов < 90 дней
- [ ] Studio, Grafana и SSH закрыты Cloudflare Access; у всех участников аккаунта Cloudflare включена 2FA
- [ ] Заголовки безопасности отдаются (оценка A на проверке заголовков), CSP без нарушений в консоли
- [ ] Последний бэкап моложе 24 ч, тест восстановления — не старше 31 дня
- [ ] Оповещения доходят (тестовое событие раз в неделю)

### 22.13. Критерии приёмки
- `harden.sh` на чистых Ubuntu 24.04 / Debian 12 в CI приводит систему к состоянию, при котором все пункты §22.12 зелёные.
- Повторный запуск `harden.sh` ничего не ломает и не блокирует доступ администратора.
- Перед публичным запуском проведён внешний тест на проникновение (или как минимум OWASP ZAP baseline + ручная проверка по OWASP ASVS уровня 1), найденные High/Critical исправлены.
- `security-check.sh` запускается по расписанию раз в неделю и присылает отчёт.

### 23.2. Встроенная помощь в игре
- **Обучение при первом заходе:** 3 подсказки-«пузыря» на экране записи (где реплика, где уровень микрофона, как перезаписать); отключаются кнопкой «Понятно» и не показываются повторно.
- **Тренировочный клип:** одиночный режим «Попробовать» на коротком клипе без комнаты — игрок проверяет микрофон и синхронизацию.
- **Контекстные подсказки** (`?` рядом с настройками комнаты, эффектами, ползунком синхронизации) ведут на нужный раздел `/help`.
- **Экраны ошибок** содержат ссылку на соответствующий пункт FAQ.

### 23.3. Структура руководства администратора (оглавление)
1. Что понадобится: сервер (2 vCPU / 4 ГБ RAM / 40 ГБ SSD минимум), домен, аккаунт Cloudflare.
2. Подключение домена к Cloudflare (смена NS-серверов).
3. Создание туннеля в Zero Trust и получение токена (с картинками).
4. Установка: `install.sh`, `setup.sh`, `start.sh` (§21.5).
5. Настройка Cloudflare Access для Clip Studio и добавление авторов.
6. Правила кеширования и HTTPS.
7. Загрузка стартовых клипов.
8. Ежедневная работа: `status.sh`, `logs.sh`, модерация жалоб.
9. Обновление и откат (`update.sh`).
10. Резервные копии и восстановление.
11. Безопасность: запуск `harden.sh` и `security-check.sh`, доступ по SSH через Cloudflare Access, добавление/удаление администраторов, ротация секретов, реакция на инцидент (§22).
12. Типовые проблемы: туннель «down», 502 от Cloudflare, закончилось место, не грузятся большие файлы в Studio, WebSocket рвётся.
13. Удаление сервиса.

### 23.4. Формат и инструменты
- Исходники — Markdown в `/docs`, сайт справки собирается VitePress и отдаётся по `/help` (тот же деплой, тот же туннель).
- Языки: RU и EN; перевод ведётся в тех же файлах локализации, что и интерфейс.
- Скриншоты и GIF снимаются автоматически Playwright-скриптом со стенда (`docs:screenshots`), чтобы не устаревали при изменении интерфейса.
- Версионирование: документация привязана к версии релиза; в `CHANGELOG.md` — раздел «Что нового для игроков».
- Команды из руководства администратора проверяются в CI (тот же прогон, что §21.8).

### 23.5. Критерии готовности документации
- Каждый сценарий US-1…US-6 покрыт инструкцией.
- Тест «с чистого листа»: человек без опыта в проекте по руководству администратора разворачивает сервис на новом VPS ≤ 60 мин без вопросов команде.
- Тест для игроков: 5 новых пользователей по «Как играть» проводят первую игру без внешней помощи.
- Все ссылки из интерфейса на `/help` ведут на существующие разделы (автопроверка битых ссылок в CI).
